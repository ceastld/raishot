# 托盘弹层（2026-10-24）

用自绘弹层替换托盘右键的系统菜单：分区不变，多给状态、尺寸、最近记录、剪贴板与贴图信息，并新增长截图、录屏入口。

- 设计稿：[design/tray-popup.html](../design/tray-popup.html)（10-24 用户确认，含长截图／录屏入口）。
- 现状：系统菜单在 `src/tray.rs::menu/show_menu`，命令分派在 `src/ui.rs` 的 `tray::EVENT` 分支。
- 结论（10-24）：自绘弹层不做。用户选择保留系统菜单，只把顶层收拢为 9 项并加主题图标（`src/tray.rs::menu`）。以下设计与测量留作参考，测速代码保留在 `src/tray_popup.rs`。

## 1. 宿主进程：第二个待命进程

| 方案 | 打开延迟 | 问题 | 结论 |
| --- | --- | --- | --- |
| A 托盘进程原生自绘（D2D／GDI） | 最快 | 托盘里多一套 UI 栈和设备，违背“界面用 GPUI”“常驻只管托盘” | 否 |
| B 复用截图待命进程 | GPUI 冷启动 | 弹层用掉唯一的截图待命，最常用的“区域截图”反而走冷启动 | 否 |
| C 常驻一个已初始化 GPUI 的进程 | 最快 | 常驻 GPU 设备与几十 MiB 内存，违背开发计划“架构约定”第 5 条 | 否 |
| **D 第二个待命进程，角色为弹层** | GPUI 初始化一次 | 多一个空闲进程（托盘＋待命目前合计约 3.7 MiB 私有内存） | **选定** |

D 的流程：

1. 托盘启动并备好截图待命后，再起 `raishot-gpui --tray-popup-standby`。待命期间同截图待命，不初始化 GPUI／D3D。启动、就绪、属主退出检查复用 `capture_standby.rs` 现有设施，只加角色参数，不另写一套。
2. 右键（或 `NIN_KEYSELECT` 键盘打开）时，托盘先 `AllowSetForegroundWindow(弹层 pid)`，再发请求：锚点、是否键盘打开、热键注册结果、截图待命是否就绪、请求 QPC。
3. 弹层进程初始化 GPUI，用确定的高度开窗（见 §4），首帧只画同步数据，其余异步填入。
4. 关闭或执行命令后进程退出；托盘在空闲约 1 秒后补一个新的弹层待命。
5. 回退：弹层待命不在、正忙、启动失败或 400ms 内没有就绪回执时，托盘照旧弹系统菜单。`tray::menu` 保留作回退，也同步补上长截图／录屏两项。

依据：GPUI 初始化是截图启动的主要耗时，截图靠原生首屏把冻结可框选压到约 200ms（`startup_surface.rs`）。P0 实测见 §9：冷启动中位约 400ms，不达标；GPUI 先在隐身窗口里画好一帧后，请求到可见中位约 14ms。

**延迟门槛**（P0 实测，从右键通知到弹层首帧呈现）：中位 ≤150ms，最差 ≤250ms。达不到时按顺序：

1. **悬停预热**：`NOTIFYICON_VERSION_4` 会送来图标上的 `WM_MOUSEMOVE`，托盘据此让弹层待命先初始化 GPUI 并建好隐藏窗口；10 秒内没右键就退出重建，每 15 秒最多预热一次。
2. 仍不达标就保留系统菜单，停止本项。

## 2. 进程间协议

- **请求（托盘 → 弹层）**：固定大小、只含标量的结构，经弹层待命的消息窗口传递。传输层沿用截图待命的做法，不传指针或集合。
- **命令（弹层 → 托盘）**：`tray_request.rs` 增加 `Request::MenuCommand(u32)`，取值沿用现有菜单 ID（`REGION`、`FULL_SCREEN`、`QUICK_ACTION_BASE + i`、`PIN_*` 等），另加 `LONG_CAPTURE`、`RECORD`。“最近”缩略图贴出复用已有的 `PinFile`／`PinRecord`。
- **托盘侧**：把 `ui.rs` 里 `match tray::show_menu(..)` 各分支提到 `run_menu_command(native, id)`，系统菜单和弹层共用一张分派表。
- **不被截进去**：弹层先隐藏窗口并 `DwmFlush`，再发命令，然后退出。托盘收到截图类命令时弹层已不可见。
- **就地操作**（切换分组、隐藏／显示本组、取消穿透）：弹层发命令后保持打开，托盘执行 `Manage` 并在 `WM_COPYDATA` 返回值里带回影响数量，弹层刷新计数。切换分组复用主界面贴图页的 `Action::SwitchGroup`。
- **再次右键**：弹层还开着时，托盘只通知它关闭，不再新开。

## 3. 长截图、录屏入口

两者现在都要先在截图会话里框选，再点工具栏（`capture_view.rs` 的 `Action::LongCapture`／`Action::Record`）。托盘入口改为“带意图的区域截图”：

- 截图参数低 4 位已用作模式（1 当前屏、2 所有屏、4 图库、8 设置），意图放在第 4–5 位：0 无、1 长截图、2 录屏。
- 意图要经过三条路径：待命 IPC 元数据加字段（`IPC_VERSION` 3 → 4）、冷启动参数 `--then long|record`、`worker_argument`。
- 触发点和快捷动作“框选源”相同：`finished_new_crop` 与首屏交接完成（`startup_handoff.rs`）后，直接分派对应 Action，失败提示沿用这两个 Action 的现有文案。
- 选区阶段在左下角提示区显示“框选要长截图的滚动区域 · Esc 取消”／“框选要录制的区域 · Esc 取消”，复用快捷动作提示的位置。
- 这部分与弹层无关，可先做，系统菜单也立即受益。

## 4. 弹层界面（GPUI）

- **文件**：`src/tray_popup.rs`（视图与键盘）、`src/tray_popup_model.rs`（快照、文案、布局高度与定位计算，纯函数可测）。共享入口（`lib.rs`、`bin/gpui.rs` 参数、`ui.rs` 分派）由一人改。
- **窗口**：无标题、不进任务栏、置顶，DWM 圆角与阴影；宽 344 DIP，高度由快照同步算出，首帧后不改尺寸。
  - “最近”一行始终占位：没有记录时显示说明，高度相同。
  - 快捷动作区按启用数量决定有无，最多显示 4 个，超出时给“全部 N”。
- **定位**：取锚点所在显示器的工作区，按任务栏所在边向内展开（底部任务栏时贴着锚点向上、右对齐），出界就翻转或夹紧；按该显示器 DPI 计算。
- **关闭**：失去激活、Esc、再次右键托盘、执行任何非就地命令。
- **键盘**：方向键按视觉位置找最近项（设计稿同一算法），Enter／空格执行，Tab 在分区间跳。焦点框只在键盘打开或按过方向键后显示。
- **主题与语言**：请求到达时读 `Preferences`，配色用 `theme::palette`，文案走 `tr!`。英文按设计稿检查截断。
- **图标**：沿用 `assets/icons`，新增 `clipboard.svg`、`power.svg`。

## 8. 风险

- **前台授权**：必须在托盘还持有右键带来的前台权利时转交，否则弹层拿不到键盘焦点，Esc 与方向键失效。
- **托盘图标在 Win11 溢出浮层里**：锚点取右键时的光标位置，弹层要盖在浮层之上，或等浮层收起后再出现，需实测。
- **托盘异常退出**：弹层待命复用截图待命的属主检查，随托盘退出，不留孤儿进程。

## 9. P0 测量结果（10-24）

**代码**：`src/tray_popup.rs`，入口 `raishot-gpui --tray-popup-standby`。
- 弹层是 344×646 的固定布局，含真实中文文字、SVG 图标、快捷动作与热键。
- 测速程序 `raishot-gpui --tray-popup-bench [--prewarm] [--runs N] [--settle-ms MS]` 扮演托盘：起待命、等就绪、静置 1.5 秒，发请求后计时，到首个成功 Present 再 `DwmFlush` 为止，然后进程退出。
- 托盘本身未接入，仍用系统菜单。

**冷启动**（待命不含 GPUI，请求到达后才初始化）。dev 配置（已优化）各 10 次，共两批：

| 阶段（自请求起，ms） | 第二批范围 | 说明 |
| --- | --- | --- |
| 待命收到请求 | 1.8–5.4 | 进程间消息 |
| `Application::new()` 返回 | 237–288 | 平台、渲染设备与字体系统初始化，单这一步已超出门槛 |
| 首次 render | 335–639 | 含主题、读设置、开窗、排版 |
| **首帧可见上界** | 中位 403，365–690 | 第一批中位 432，343–673 |

- 空闲待命：私有内存 2.8 MiB，工作集 10.9 MiB。
- 结论：中位 ≈ 400ms，远超“中位 ≤150ms”。只换宿主进程而不预热的方案不成立。

**预热后**（GPUI 已启动，弹层在 DWM 隐身窗口里画好一帧，请求到达后只移动、显形、重画）。连续两批各 10 次，全部成功：

| 指标 | 结果 |
| --- | --- |
| 请求 → 首帧可见上界 | 中位 13.7／14.0ms，9.8–18.8ms |
| 预热耗时（起进程 → 隐身帧画好） | 359–526ms，其中起进程约 35ms |
| 预热后常驻内存 | 私有 52.7–56.8 MiB，工作集 59–67 MiB |

调试中发现并修正的两点，P1 需保留：
- **激活与关闭**：隐身窗口偶发被激活后又失活，原“失活即关闭”会让它在请求前退出，未修复时 1/7 失败。改为只有显示后才把失活当作关闭。
- **唤醒方式**：请求改用 oneshot 唤醒 GPUI，不再用定时器轮询。轮询受约 15ms 计时器粒度影响，曾使中位为 28ms。

**测量边界**：
- 只在本机测过，用户同时在用电脑。
- 用测速程序代替托盘：未含 Shell 通知到托盘的一两毫秒，也没有前台授权，弹层以不抢焦点方式显示。
- 静置只有 1.5 秒，长时间空闲后页面被换出的情况未测。
- 弹层内容固定，P2 的后台数据加载不计入首帧。

**怎样预热**：见 §10 的拆分与结论。

## 10. 冷启动拆分与预热决定（10-24）

**工具**：
- `raishot-gpui --tray-popup-d3d-probe [--adapter N] [--preload a.dll,b.dll] [--debug-flag]` 在全新进程里单测 DXGI 工厂与 D3D11 设备创建，并列出新加载的模块。
- 整体拆分用现有的 `RUSTSHOT_STARTUP_TRACE=1`。
- 新增 QA 开关 `RUSTSHOT_GPUI_GPU_PREFERENCE=minimum_power`，让 GPUI 按省电顺序选显卡，见 vendor/README。

本机是混合显卡笔记本：适配器 0 为 NVIDIA RTX 4060 Laptop，另有 Intel UHD 核显。GPUI 默认取适配器 0。

**`Application::new()` 的 240–290ms 去向**（默认选 NVIDIA）：

| 部分 | 耗时 | 说明 |
| --- | --- | --- |
| D3D11 设备创建 | 192–237ms | 进程内第一个设备的代价：同进程第二个设备只要 31–36ms |
| ↳ 其中驱动 DLL 加载 | 60–75ms | 预先 `LoadLibrary` 驱动模块后，首个设备降到 129–141ms |
| ↳ 其中首个设备的驱动初始化 | 约 130ms | 预载无法去掉，推测含唤醒独显 |
| DXGI 工厂 | 26–42ms | — |
| 系统字体集合 | 123–154ms | 与设备并行，NVIDIA 时被设备耗时盖住 |

没有调试层：本机无 `d3d11sdklayers.dll`，测量也未带调试标志。

**能否压到 100ms 以下**：
- **NVIDIA**：不能。即使预载驱动 DLL，工厂加设备仍约 165–175ms。
- **核显**：设备降到 39–55ms，但字体成为关键路径（主线程等字体 48–63ms），`Application::new()` 为 146–182ms。把字体集合挪到待命进程预备（纯 CPU）也许能到 100ms 左右，未测。
- **整体仍不达标**：初始化之后，开窗并画第一帧还要 130–175ms：

| 开窗部分 | 耗时 |
| --- | --- |
| 同步显示窗口（`SetWindowPlacement`） | 63–102ms |
| 建渲染器（主要是着色器管线） | 33–43ms |
| 首次绘制 | 17–28ms |
| 拖放注册 | 约 9ms |

  核显冷启动整体实测：中位 357ms（320–463ms，10 次）。即使初始化降到 100ms，冷启动也约 250ms，过不了中位 ≤150ms。

**预热的实测代价**：

| 指标 | NVIDIA | 核显 |
| --- | --- | --- |
| 预热完成耗时（起进程起） | 359–526ms | 380–580ms |
| 预热后请求 → 可见 | 中位 14ms | 中位 14.7ms（12.4–19.0ms） |
| 预热后常驻私有内存 | 约 55 MiB | 约 60 MiB |

- 空闲时预热进程不重画（呈现串号 8 秒内不变），但持续占一个核约 4%：15 秒内 594ms CPU，核显。原因未查清，可能是 GPUI 每帧的 vsync 唤醒，或主题每秒读一次设置。
- 预热阶段起初约 3 秒里呈现了约 210 帧，也需要查。

**决定**：
- **悬停预热不采用**：预热要 0.4–0.6 秒，而从鼠标进入托盘图标到右键通常更短（本机未实测）。多数点击仍要等，往往接近冷启动，不能稳定达标。
- **只有常驻预热能达标**。采用前须同时满足以下条件；做不到就按原计划保留系统菜单，停止本项：
  1. **弹层固定用核显**（省电优先的适配器）：不让常驻设备一直占着独显，避免耗电。这需要把 QA 开关改成弹层进程的正式选项。
  2. **空闲 CPU 降到接近 0**：查清并去掉约 4% 的空闲唤醒。
  3. **用户同意放宽规则**：开发计划“架构约定”第 5 条（常驻只管理原生托盘），接受常驻多约 60 MiB 私有内存。
